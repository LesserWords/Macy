# M0 — Foundation (weeks 1–2)

**Goal:** an empty but fully gated, containerised, multi-workspace skeleton with the LLM path proven.

**Exit gate:**
- CI enforces every gate.
- A "bad sample" branch fails each gate.
- Schema v1 is migrated, and a second workspace sees 0 rows from the first.
- The ADR-001 (DBOS) and ADR-007 (OpenRouter) spikes are decided.

---

## M0-01 — Repository, CI skeleton, OpenSpec
**Features:** — · **ADRs:** 006, 019, 020 · **Depends:** — · **Size:** 1 day

Steps:
1. Create the GitHub repo. Run `uv init`, set Python 3.12+, and configure ruff + mypy in `pyproject.toml`.
   → verify: `uv run ruff check . && uv run mypy engine` passes on an empty package.
2. Add `scripts/check.sh` as the single entry point, plus pre-commit (ruff, mypy, gitleaks).
   → verify: `pre-commit run --all-files` is green, and a planted fake key is blocked by gitleaks.
3. Run `openspec init`. Add the CI job `openspec validate`.
   → verify: CI fails on a deliberately malformed spec and passes after it is fixed.
4. Add `.github/workflows/ci.yml` with the jobs `check`, `test` and `openspec-validate`.
   → verify: the first PR shows all three as required checks.
5. Set up branch protection (required checks, linear history, squash) and a PR template from [templates/pr-plan.md](../templates/pr-plan.md). Configure Dependabot.
   → verify: a direct push to `main` is rejected.

**Done when:** a trivial PR passes all checks and merges through the template.

## M0-02 — Remaining quality gates
**ADRs:** 006, 018, 025 · **Depends:** M0-01 · **Size:** 1 day

Steps:
1. Add complexipy (≤ 15, ratchet), vulture (confidence ≥ 80, plus a whitelist), jscpd (≤ 3 %), import-linter (initial contracts) and the PLR limits.
   → verify: each tool runs from `scripts/check.sh`.
2. Add pytest + pytest-cov (≥ 90 % branch coverage) + diff-cover (100 % of changed lines) + a Hypothesis CI profile (derandomized).
   → verify: `uv run pytest` reports coverage, and diff-cover runs against `origin/main`.
3. Add the CRAP-style hotspot script and upload the trend artefacts.
   → verify: CI artefacts contain the complexity, duplication and coverage JSON.
4. Create the "bad sample" branch: a function with CC 12, a duplicated block, an unused function, a cyclic import and an untested line.
   → verify: CI fails, with each gate naming its violation (screenshot in the PR). Then delete the branch.

**Done when:** every gate in PRD §9.3–9.4 is proven to block.

## M0-03 — Docker image, Compose files, Postgres, migrations runner
**Features:** F20 · **ADRs:** 011, 012 · **Depends:** M0-01 · **Size:** 1.5 days

Steps:
1. Write a `Dockerfile` (multi-stage, uv, non-root user) producing one image for both app and worker.
   → verify: `docker build` succeeds, and the image runs `python -c "import engine"`.
2. Write `compose.yaml` with `db` (pinned postgres 18.x, or 19.x if GA, plus a healthcheck), `migrate` (dbmate one-shot), `app` and `worker` (placeholder).
   → verify: `docker compose up -d` brings every service healthy, and `migrate` exits 0.
3. Write `compose.override.yaml` (dev), `compose.e2e.yaml` (webhook receiver + fake OIDC placeholders) and a `compose.prod.yaml` skeleton (caddy, backup).
   → verify: the CI job `compose-config` runs `docker compose config` for each combination.
4. Wire squawk into pre-commit and CI for `db/migrations/*.sql`.
   → verify: a migration with a plain `CREATE INDEX` on an existing table is flagged.
5. Make sure the dev workflow is documented: `docker compose up` is the only setup step.
   → verify: a fresh clone with only Docker installed runs the app placeholder.

**Done when:** every environment starts from the same image via Compose.

## M0-04 — Schema v1 (tenancy, config, events, usage)
**Features:** F01, F17 · **ADRs:** 009, 010, 011 · **Depends:** M0-03 · **Size:** 1.5 days

Steps:
1. Write a migration for `workspaces`, `users` (with `ui_locale`), `memberships`, `brand_profiles`, `campaigns`, `sources`, `workspace_integrations`, `webhook_subscriptions`, `events`, `webhook_deliveries`, `usage_ledger`, `llm_payloads` and `runs`, exactly as in DATA-MODEL §3.
   → verify: squawk is clean, and `db/schema.sql` is committed and diffed in review.
2. Add the database roles `owner`, `app`, `retention`, `readonly`, and `REVOKE UPDATE, DELETE ON events FROM app`.
   → verify: a test running as `app` gets a permission error when updating `events`.
3. Write the tenant-scoping test: it parses every SQL statement in `engine/db.py` and requires `workspace_id`; it seeds 2 workspaces and checks for cross-reads.
   → verify: the test fails on a planted unscoped query, then passes once the query is removed.
4. Write constraint tests: composite FKs reject a cross-workspace reference; `UNIQUE NULLS NOT DISTINCT` on `sources`; `runs_one_active`.
   → verify: each violation raises the expected `IntegrityError` (literal SQLSTATE asserted).

**Done when:** the schema enforces isolation and invariants at the database level.

## M0-05 — Contracts, packs loader, services skeleton, capability specs
**Features:** F01, F03 · **ADRs:** 009, 014, 020 · **Depends:** M0-04 · **Size:** 1.5 days

Steps:
1. Write `contracts.py`: `ResearchRecord`, `Opportunity`, `EditorialBrief`, `ContentDraft`, `QualityReport`, `PublishRequest`, `PublishedContent`, `BrandProfile`, `CampaignConfig`, `KeywordData`, each with `schema_version`.
   → verify: unit tests for validation (Hypothesis for `CampaignConfig` weights summing to 100).
2. Write `config.py` to load and validate the git packs (industry, format, prompts) and compute `pack_version` (a hash).
   → verify: a broken pack fails with an error naming the file and field.
3. Write a `services.py` skeleton with `require_member()`, plus the import-linter contracts (`app`/`cli` → services + contracts only; SQL only in `db`).
   → verify: a planted `import engine.db` in `app.py` fails CI.
4. Seed the OpenSpec capability specs from F01–F20 (acceptance criteria → WHEN/THEN).
   → verify: `openspec validate` is green, with one spec per capability listed in the features index.

**Done when:** contracts and the service boundary exist and are enforced.

## M0-06 — Ports, plugin registry, fakes, contract suites, integration config
**Features:** F05 · **ADRs:** 005, 008 · **Depends:** M0-05 · **Size:** 1.5 days

Steps:
1. Write `integrations/ports.py` (7 Protocols) and `registry.py` (entry-point discovery), plus `cli plugins list`.
   → verify: `cli plugins list` shows the fakes registered through `pyproject.toml`.
2. Write `fakes.py` (one fake per port) and the contract-suite harness parametrised over registered plugins.
   → verify: the fakes pass every contract suite.
3. Write `plugin_config(workspace_id, port)` over `workspace_integrations`, with Fernet encryption (MultiFernet) and `cli integrations set` / `rotate-key`.
   → verify: round-trip tests; secrets are absent from `repr`, logs (caplog) and service return values; rotate-key keeps the secrets readable.
4. Handle a missing integration by raising `IntegrationMissing(port)`.
   → verify: a unit test checks that the message names the port.

**Done when:** vendors are swappable by configuration only, and secrets are safe.

## M0-07 — LLM port, OpenRouter plugin, Instructor helper, usage ledger (ADR-007 spike)
**Features:** F05, F17 · **ADRs:** 002, 007, 016, 023 · **Depends:** M0-06 · **Size:** 1.5 days

Steps:
1. **Spike (½ day, throwaway script):** call OpenRouter for Opus 5.5 and Haiku 5.5 with our `Opportunity` schema through Instructor (`require_parameters`).
   → verify, recorded in ADR-007: exact model ids; schema-valid output; `cached_tokens` > 0 on the second call; `usage.cost` present. If anything fails → plan the `anthropic_direct` fallback.
2. Write the `openrouter` plugin (Settings: api_key, model per stage, data policy) and `llm.py` (`structured_call(stage, model_cls, prompt, input)`: retries ≤ 2, JSON-mode fallback, stable cached prefix, `session_id` = run_id).
   → verify: the contract suite passes against recorded HTTP; the fake LLM passes too.
3. Write ledger rows to `usage_ledger` (+ `llm_payloads`) for every call, with cost taken from `usage.cost`.
   → verify: a test asserts the ledger row fields, with exact `numeric` cost.

**Done when:** a structured call through OpenRouter is proven and logged with its cost.

## M0-08 — `safe_http`, Sentry, heartbeat
**Features:** F20 · **ADRs:** 008, 023 · **Depends:** M0-03 · **Size:** 1 day

Steps:
1. Write `safe_http`:
   - HTTPS only in prod;
   - DNS resolved, then private, loopback, link-local and metadata ranges refused;
   - 10 s timeout, 1 MB cap, no cross-host redirects.
   → verify: Hypothesis over the IP ranges, plus literal cases (`169.254.169.254`, `127.0.0.1`, `10.x`, `::1`, DNS rebinding → refused).
2. Add the Sentry SDK (DSN from env), with a `before_send` hook that scrubs secrets, and tags for `workspace_id` / `run_id`.
   → verify: a test asserts the scrubber removes `api_key` / `Authorization` values.
3. Add the heartbeat ping helper (URL from env, no-op when unset).
   → verify: a unit test with a fake HTTP client.

**Done when:** outbound user URLs are safe, and errors and missed runs are visible.

## M0-09 — DBOS spike → ADR-001 decision
**Features:** F18 · **ADRs:** 001 · **Depends:** M0-04 · **Size:** ½ day

Steps:
1. Implement a 2-stage toy pipeline (research → score with fakes) twice: hand-written state machine vs DBOS workflows on the same Postgres.
   → verify: the same test suite (failure isolation, resume, one active run) runs against both.
2. Compare lines of code, test effort and operational needs (system tables, upgrades).
   → verify: a comparison table is written into ADR-001, with Status updated to "A confirmed" or "B adopted".

**Done when:** ADR-001 is final, and the M1-10 scope reflects the choice.
